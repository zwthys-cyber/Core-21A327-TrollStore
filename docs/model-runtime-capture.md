## v2 采集入口排查

v1 的两次新报告均为窗口结束、读取计数零、快照为空。其中一轮的原日志确认后端就绪，且窗口结束前原骨骼缓存已有有效关节；这不能证明采集入口已执行，也不能单从零计数判断网格或姿态不存在。

读取已发布 v1 的有限指令发现：采集大数组被内联进清零转发函数，转发入口分配约 32 KiB 栈，调用 Darwin 栈探测之后才把 x30 作为 `__builtin_return_address(0)` 的来源。当前报告在调用地址匹配之前没有计数，无法区分入口未执行、调用位置不匹配和窗口过期。这是此次修复的依据；具体实机零计数原因仍需 v2 报告验证。

v2 在 ARM64 入口用 x4 显式传递原 LR；将大数组采集函数设为不内联，普通清零路径保持小栈。新增入口总次数、未匹配调用次数、窗口关闭后读取次数及递归读取次数，保留原帧布局与采样限额。云端除原生转发/递归/errno 检查外，对实际设备包入口建立合成 ARM64 调用帧，检查 LR、FP、原参数、SP 和小栈路径；不执行手机或游戏。

v2 本次实机报告已确认采集成功，具体范围见下文。初始化成功、入口次数非零、读取次数非零、实际快照非空分别表示不同阶段，不能相互替代。已有网格绑定和逐像素深度字段为明确的未验证声明，并非动态检测结果；`game_process_started=false` 表示采集工具不主动启动游戏，不能解释为用户没有打开游戏。

v2 排查构建源码为 `872f141c2e1805de2e8732e1c3a87a73612e2bf1`，隔离分支为 `fix/model-capture-entry-v2`。[采集构建 38566467709](https://github.com/zwthys-cyber/Core-21A327-TrollStore/actions/runs/38566467709) 全部通过，包括 37 项 Python 回归、实际转发入口的原生采样/递归/errno 检查、设备包签名及编译后的 ARM64 入口检查；[普通构建 38566471442](https://github.com/zwthys-cyber/Core-21A327-TrollStore/actions/runs/38566471442) 也全部通过。下载的 v2 包为 7,208,937 字节，SHA-256 `73cc0a58ce650f67718594bec52bcbd050b8bde39caddd68e9fe4cd123d9b9f6`，与云端元数据一致。有限指令复核确认转发函数栈为 64 字节，且原 LR 在首次 C 调用前已通过 x4 保存。正式最新 Release 仍为 v19。

新报告的 `capture_version` 应为 2。入口总次数为零需继续检查转发是否执行；入口非零而读取次数为零需检查调用点是否匹配；读取次数非零但快照为空时，结合窗口关闭次数、组件次数和跳过码区分后续条件。入口次数、未匹配次数及读取次数在窗口关闭后仍可能增长，但最终文件仅保存窗口结束时的读数；各项计数独立读取，不是原子的同一帧状态。

## 手机操作

1. 用 TrollStore 覆盖安装云端构建的 `Core-17.0-21A327-TrollStore-model-capture-v5.ipa`。
2. 打开 Core，正常初始化内核、获取信息和开启悬浮菜单。
3. 进入游戏并让附近人物出现在画面中，随后移动至墙体遮挡目标的视角并观察至少 10 秒。采集窗口从 Core 启动后开始，约三分钟；若初始化耗时超过窗口，重新打开 Core 后再进入游戏。
4. 从“文件 → 我的 iPhone → Core”取出 `Core-model-runtime-report.json`，放到 `/root/core`。报告也会在没有成功样本时写入观察次数和跳过原因；无需再次导出静态资源包。

## 读取与报告边界

只在可选版本中，将 Core 原 `_bzero` 导入映射到相同 ABI 的转发函数；原代码、导入 stub、系统调用和返回地址不移动。转发保持清零参数、结果及 errno。ARM64 入口用尾跳转携带调用者帧指针、远程地址寄存器和原 LR，正常调用在转发后不触发采集。

采集仅接受原 Core UUID、读取器 `E1908` 的首次清零调用、原骨骼采集器 `D897C` 调用后返回位置 `D8980`、44 字节组件变换目的缓冲，以及经过边界检查的帧布局。数组指针、数量来自原采集器刚读到的结构；步长从原配置取得。最多读取 256 个、44/48 字节步长的变换，完整保存所定位组件声明的数组，不能据此证明已包含人物所有附件组件或衣服形变。

每个组件最多两个样本，v3/v4/v5 相隔至少 10 秒（v1/v2 为两秒），最多三个组件、六个样本。变换读取在原采集线程完成；数据复制后交给独立串行队列写报告，避免异步访问失效的栈和变换缓冲。报告写入应用自己的 Documents，最多 2 MiB，不发送网络请求。

另对已经定位的同一骨骼组件读取布局样本，用于识别其网格引用字段：v1/v2 为 2 KiB，v3/v4 为 4 KiB。v4 优先保存资源及附件候选，每个最多 4 KiB、12 个候选、40 次读取；按类前缀中的大小及对齐提示限制读取，失败时保留已取得的对象头。此提示不是已验证的类型布局。仅在地址、数量、容量同时匹配时记录实际姿态数组的布局槽位；不递归扫描候选对象的其他指针。这些样本以 Base64 写入本地报告，读取失败不影响已取得的姿态。报告明确标记布局及候选尚未经过语义类型解释，不能据此宣称已定位实际渲染网格。

世界位置由组件变换和组件空间的骨骼平移计算，二维位置通过原 Core 投影函数取得。报告没有引擎帧编号，不宣称多个远程读取组成了原子的同一引擎帧快照。

v5 的布局仍为 4 KiB，候选上限为 16 个对象/56 次读取，附件数组最多前 16 项；额外固定资源关系最多 16 条/56 次对象读取。主资源五组候选数组最多各 256 项/8 次读取，单缓冲最多 16 KiB。名称查找按已核对的原 Core `D6794` 实时 profile 路径取得，最多 128 个条目/32 个分块缓存/320 次读取，每条最多 256 字节且必须为有终止符的 ASCII。以上额外读取不受射线的 10 ms 预算约束，只在最多六个采样中执行；读取次数和失败、截断均写入报告。数组步长和语义身份仍是待验证假设，失败不影响已取得姿态。

遮挡样本使用原几何场景的同一锁及射线查询入口。只有几何就绪、三个场景均存在时查询，记录相机至关节点的命中/未命中和原世界单位的距离。逐次查询之间检查约 10 ms 的预算，达到预算后保留未知值及截断标记；该预算不能中断已经进行的原锁或射线调用。它不是游戏 GPU 的逐像素深度纹理，也不是身体填色已经完成的证明。

## 静态分析依据

- 原 `D897C` 通过 `E1908` 读取 44 字节组件变换，数组指针在调用者 `SP+0x110`、数量在 `SP+0x118`。
- 原 `E1908` 的帧指针为其入口 SP 减 16，原保存的组件指针在 `FP-0x48`、采集上下文在 `FP-8`。`E195C` 调用清零后返回 `E1960`；所有检查均先于额外读取。
- 原骨骼批量读路径 `D8DAC..D8DD0` 检查配置步长 48，并读到最后所需骨骼的 44 字节有效部分。本采集版保存完整声明数量，不改原骨骼选择或绘制。
- `D33F4` 使用 `BD4F78` 的共享锁访问三个本地几何场景。`E0BE8/E0CF0` 的返回缓冲为 80 字节，距离在偏移 32，几何 ID 在偏移 72。原判定用几何 ID 是否为 `UINT32_MAX` 区分命中。

已有 21 份静态服装及附件的 LOD0 顶点、索引、蒙皮权重和参考骨骼解码，但当前完整基础身体资源、运行时网格绑定及像素级轮廓渲染仍未完成。实机数据采集是继续核对这些连接的输入。
