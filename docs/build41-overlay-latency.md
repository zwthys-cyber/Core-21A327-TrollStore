# 方框和填色跟随延迟 · v13 / build 41

用户进一步澄清：此前称为“闪烁”的主要观感是移动／转视角时标记跟随有延迟、轮廓一晃一晃；方框也有延迟。因此排查范围扩大到整个悬浮标记的更新与提交，不能继续将其只描述为填色投影误拒绝。没有获得 v11/v12 的新实机状态报告。

## 已确认的代码事实

`CoreModelRenderDispatch` 先执行原 `DB144` 方框／姓名／射线／载具采集和绘制，再同步执行 `CMLDraw`，随后才返回原 ImGui/Metal 提交路径。新增填色计算耗时会推迟同一批方框等标记的提交。v10 旧实机报告中的新增填色阶段平均约 26.4 ms、最高约 67.5 ms；该历史数据不能当作 v12 的测量结果，也不能据此确定本次所有延迟的唯一原因。

另外，之前实时版启动仍会开启独立的 180 秒详细模型采集，最多六份姿态／资源／流缓冲快照，和实时流程使用同一远程读取后端。当前绘制已经每帧重新读姿态；观察器的 50 ms 节流不是最终动画姿态只更新 20 Hz 的依据。相机在填色阶段重新复制的是 Core 的本地缓存，不等同于从游戏取得一份新引擎帧；原有“camera age”计时只测本地复制后的时间。

## 改动

1. “位置”增加独立的 **人物填色** 开关。它和“附近敌人”“附近载具”分别保存。保持敌人开关开启、关闭人物填色时，方框、姓名、射线和载具仍按原路径绘制，附加填色观察器不读取游戏模型，填色不执行蒙皮、栅格和逐像素查询。
2. 本实时构建不再自动开启 180 秒详细模型／缓冲采集。保留 `Core-model-render-status.json` 定时状态和原独立采集构建；本实时包的 `Core-model-runtime-report.json` 会注明详细采集未启用。
3. 分别记录填色开／关两组回调数、原绘制耗时、整个回调耗时和同模式连续回调间隔。保留填色各阶段耗时，并明确回调数据不包括后续 Metal/屏幕提交、游戏画面延迟；间隔含空闲时间，不能直接换算游戏 FPS。本地相机复制时间也不再被解释为真实游戏相机年龄。
4. 开启人物填色时继续使用原全分辨率逐像素算法、原红白判断和 600 米上限，不复用旧屏幕填色或预测目标位置。

新开关复用原被合并的射线布尔槽 `+0x20`；原射线渲染已固定使用 `+0x23` 的附近敌人开关。UI 仅修改 v12 已旁路的菜单区域，三个控件都继续设置原 dirty 标志，并匹配一次 BeginChild/EndChild。已有车辆筛选、文字、人物标记指令不变。

## 实机复核

覆盖安装后，先打开“附近敌人”与所需的“附近载具”，**关闭人物填色**，移动和转视角观察方框。之后在相近场景开启人物填色，比较跟随，并导出 `Core-model-render-status.json`。状态应为 `render_version=13`；确认 `detailed_capture_enabled=false`，观察两组计数都增长，再分别用总耗时／对应回调数评估。

这是一次移除额外采集、提供可用关闭路径和分离延迟来源的改动，**不是已证实消除填色开启时全部延迟的修复**。若关闭填色后方框仍明显拖后，需要继续排查原始采集、视图缓存及提交帧率；若仅开启填色时拖后，则根据新阶段时间继续缩短同步工作。此前远距敌人漏显也未由本次改动确认修复。

编译和自动化检查只在 GitHub Actions 执行。新增原生合成回归验证关闭填色时原绘制仍执行且附加远程读取、场景查询为零；开关恢复后全精度填色继续；分组耗时保留原路径本身的慢帧；三个菜单开关在 64 组状态／点击组合下互不覆盖并正确保存。既有红白、移动、姿态、LOD、栅格和签名检查继续执行。
